# 14. Memory and Reference Model

## 14.1 Overview

LLMK uses a simple and deterministic memory model.

Values, variables, and references are distinct concepts.

The language minimizes implicit sharing to improve readability, safety, and AI-assisted code generation.

---

## 14.2 Value Semantics

Values are passed by value by default.

The observable behavior of passing a value to a function shall be equivalent to pass-by-value.

Modifying a parameter shall not reassign or otherwise modify the caller's variable.

A TYPE value may contain mutable fields. Changes to a parameter's fields shall not be observable through the caller's value unless the parameter is declared using REF.

Example:

```llmk
FUNCTION User.Process(
    User user
)

user.age = 30

NONE
```

Changes to `user.age` inside `User.Process` shall not modify the caller's `User` value.

---

## 14.3 Reference Semantics

References are explicit.

A reference shall be declared using the `REF` keyword.

REF may only appear in a function parameter list.

Example:

```
FUNCTION User.UpdateAge(

    REF User user

    INT age

)

user.age = age

NONE
```

The function modifies the caller's variable through the reference.


A LET variable holding a TYPE instance may be passed to a REF parameter when the intended operation modifies only the instance's fields.

The called function shall not reassign the REF parameter when the caller's variable is declared using LET.

The distinction between modifying a TYPE instance's fields and reassigning the variable holding that instance shall be preserved.

Example:

```llmk
FUNCTION User.UpdateAge(
    REF User user
)

user.age = 30

NONE
```

The function may be called with a LET variable:

```llmk
LET User user = User("Alice", 20)

User.UpdateAge(user)
```

The call modifies the field of the existing TYPE instance. It does not reassign the LET variable.

If a function reassigns its REF parameter, it shall not be called with a LET variable as that argument.


---

## 14.4 Local Variables

Local references are not supported.

The following is invalid:

```
REF User user
```

Only function parameters may use `REF`.

---

## 14.5 Assignment

Assignment changes the value held by a mutable variable.

LET variables cannot be reassigned.

VAR variables may be reassigned.

Fields of a TYPE instance may be modified regardless of whether the variable holding the instance was declared using LET or VAR.

Modifying a field does not reassign the variable holding the TYPE instance.

When a TYPE value is passed by value, modifications to its fields shall not be observable through the caller's value unless the parameter is declared using REF.

---

## 14.6 Shared Mutable State

Shared mutable state shall be explicit.

LLMK does not provide implicit shared references.

Sharing mutable data requires a REF parameter.

---

## 14.7 FOR

FOR invokes a function sequentially for each element in the input collection.

The invoked function shall accept the current element as its first parameter.

The function may optionally accept one REF parameter as its second parameter.

The second parameter shall be a REF parameter, and its type shall match the corresponding function parameter declaration.

Example:

```llmk
VAR Statistics statistics = Statistics()

FOR users User.Validate(statistics)
```

Conceptually, each iteration invokes the function with the current element and the referenced value:

```llmk
User.Validate(user, statistics)
```

The iterations execute sequentially.

---

## 14.8 PARFOR

PARFOR executes each iteration independently.

The invoked function shall accept exactly one parameter.

REF parameters are not permitted.

Example:

```
LET ARRAY RESULT User results =
    PARFOR users User.Validate()
```

The execution order is unspecified.

PARFOR waits for all iterations to complete.

Returned values are collected into an array preserving the input order.

Failures in one iteration shall not prevent the execution of the remaining iterations.

---

## 14.9 Deterministic Behavior

The memory model is deterministic.

The language avoids implicit aliasing and hidden shared state.

This improves readability, compiler implementation, and AI-assisted program generation.

---

## 14.10 Design Principles

The memory model follows these principles.

- Value semantics by default.
- References are explicit.
- REF is limited to function parameters.
- Shared mutable state is explicit.
- PARFOR does not permit shared mutable state.
- Deterministic behavior is preferred over implicit optimization.
