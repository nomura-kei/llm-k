# 8. Error Handling

## 8.1 Overview

LLMK represents recoverable operations explicitly.

The language provides two built-in types for this purpose:

- OPTIONAL
- RESULT

OPTIONAL represents the absence of a value.

RESULT represents the success or failure of an operation.

Error handling is explicit and deterministic.

The Error TYPE is defined by the standard library.
---

## 8.2 OPTIONAL

OPTIONAL represents either:

- A value
- NONE

Example:

```
OPTIONAL User
```

Functions returning OPTIONAL shall explicitly return either a value or NONE.

---

## 8.3 RESULT

`RESULT T` represents either a successful value of type `T` or an error value of the standard library `Error` TYPE.

RESULT construction is defined in `04.Built-in_Type_System.md`.

A RESULT value shall be constructed explicitly using `SUCCESS(value)` or `ERROR(error)`.

A RESULT value shall not have an implicit default value.

The successful value or error shall be accessed through `MATCH_RESULT`.

Example:

```llmk
LET RESULT User result = User.Load(id)

MATCH_RESULT result
    SUCCESS(user) User.Save(user)
    ERROR(error) Logger.LogError(error)
```

---

## 8.4 Error TYPE

The `Error` TYPE is defined by the standard library, not by the language's built-in type system.

Its fields and APIs are specified in the Standard Library Specification.

The error value used by `ERROR(error)` shall have the standard library `Error` TYPE.

Programs should use the standard library's error information to identify errors and provide diagnostic messages.

---

## 8.5 MATCH_RESULT

`MATCH_RESULT` evaluates a value of type `RESULT T` and invokes exactly one function for the corresponding case.

The statement shall contain exactly two cases, in this order:

- `SUCCESS(value)`
- `ERROR(error)`

Each case shall contain exactly one function invocation.

The target expression shall be evaluated exactly once.

The variable declared in `SUCCESS(value)` is bound to the successful value of type `T`.

The variable declared in `ERROR(error)` is bound to the error value of the standard library `Error` TYPE.

Each case variable is available only within its corresponding case and function invocation.

`DEFAULT` is not supported in `MATCH_RESULT`.

Example:

```llmk
MATCH_RESULT result
    SUCCESS(user) User.Save(user)
    ERROR(error) Logger.LogError(error)
```

Automatic error propagation and exception handling are not supported.

---

## 8.6 Error Propagation

LLMK does not provide automatic error propagation.

Functions shall explicitly handle RESULT values using `MATCH_RESULT` when the result must be inspected.

Example:

```llmk
LET RESULT User result = User.Load(id)

MATCH_RESULT result
    SUCCESS(user) User.Save(user)
    ERROR(error) Logger.LogError(error)
```

A function may pass a RESULT value to another function without inspecting it, provided that the receiving function accepts the corresponding type.

Errors are represented explicitly through RESULT rather than exceptions.

---

## 8.7 Design Principles

The error handling system follows these principles.

- Success and failure are explicit.
- Error handling is deterministic.
- Errors are represented by a single standard Error TYPE.
- Automatic exception propagation is not supported.
- MATCH_RESULT provides explicit branching for RESULT values.
- Error handling is easy to understand for both humans and LLMs.

LLMK does not support exceptions. Recoverable failures are represented explicitly by RESULT.
