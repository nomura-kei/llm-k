# 2. Lexical Structure

## 2.1 Source Files

LLMK source files shall use the `.llmk` file extension.

Each source file defines exactly one module.

---

## 2.2 Character Encoding

Source files shall be encoded using UTF-8.

Line endings may use either LF or CRLF.

Implementations shall treat both formats equivalently.

---

## 2.3 Whitespace

Whitespace separates language tokens.

The following characters are considered whitespace.

- Space
- Horizontal tab
- Line break

Multiple consecutive whitespace characters are treated as a single separator, except inside string literals.

---

## 2.4 Statements

A simple executable statement shall occupy exactly one physical line.

The following constructs may span multiple lines according to their specific syntax rules:

- Parenthesized constructs, where line breaks are permitted inside parentheses.
- Multi-line control-flow constructs, including `MATCH` and `MATCH_RESULT`, where each case occupies a separate line.
- Other constructs explicitly defined as multi-line in this specification.

Line breaks outside these permitted constructs terminate a statement or construct according to its syntax.

Arbitrary line continuation is not supported.

This rule minimizes structural ambiguity and improves readability for both humans and LLMs.

---

## 2.5 Multi-line Constructs

Multi-line syntax shall be permitted only where explicitly defined by this specification.

Within a parenthesized construct, line breaks may appear between its syntactic elements. This includes function parameter lists, function arguments, TYPE instance creation, and other constructs whose syntax explicitly uses parentheses.

Example:

```llmk
FUNCTION User.Create(
    STRING name
    STRING email
)
```

Example:

```llmk
LET User user = User(
    name
    email
)
```

Multi-line control-flow constructs use their explicitly defined line structure. For example, `MATCH` and `MATCH_RESULT` consist of a header followed by case lines.

A line break does not implicitly continue an arbitrary expression or statement.

Blank lines may be used between statements and between permitted multi-line elements where the relevant construct allows them. Blank lines do not change program semantics.

---

## 2.6 Parentheses

Parentheses shall be used only where explicitly permitted by the language syntax, including:

- Function parameter lists
- Function arguments
- TYPE instance creation
- RESULT construction using `SUCCESS(...)` or `ERROR(...)`
- Other constructs explicitly defined to use parentheses

Parentheses shall not be used to control expression evaluation order.

Expressions shall follow the operator rules defined in `11.Expressions_and_Operators.md`.

Valid:

```llmk
User.Create(name, email)
```

```llmk
LET INT result = a + b
```

Invalid:

```llmk
LET INT result = (a + b)
```

```llmk
LET BOOL valid = (a == b)
```

---

## 2.7 Comments

Comments begin with `#`.

A comment occupies the entire line.

Inline comments are not supported.

Example:

```
# Validate user input

LET BOOL is_valid = Validate(user)
```

Invalid:

```
LET BOOL is_valid = Validate(user) # Validate user
```

---

## 2.8 Semicolons

Semicolons are not supported.

Statements are terminated by line breaks.

---

## 2.9 Identifiers

Identifiers shall begin with a letter or underscore.

Subsequent characters may contain:

- Letters
- Digits
- Underscores

Identifiers are case-sensitive.

---

## 2.10 Reserved Keywords

The following keywords are reserved.

```
TYPE
FUNCTION

LET
VAR
REF

IF
MATCH
FOR
PARFOR

TRUE
FALSE
NONE

OPTIONAL
RESULT
ARRAY

ERROR
BOOL
INT
DOUBLE
STRING
```

Reserved keywords shall not be used as identifiers.

---

## 2.11 Language Philosophy

The lexical structure follows these principles.

- One executable statement per line.
- Explicit structure over compact syntax.
- Minimal punctuation.
- Deterministic parsing.
- Readability for both humans and LLMs.
