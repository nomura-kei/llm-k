# 7. Control Flow

## 7.1 Overview

LLMK provides four control flow constructs.

- IF
- MATCH
- FOR
- PARFOR

Control flow is expressed by function invocation rather than executable blocks.

---

## 7.2 IF

IF conditionally invokes one function.

The condition shall evaluate to BOOL.

The invoked statement shall be exactly one function call.

Example:

```
IF is_valid User.Save(user)
```

ELSE is not supported.

Nested executable blocks are not supported.

---

## 7.3 MATCH

MATCH selects exactly one function invocation based on the value of an expression.

The target expression shall evaluate to `INT`, `STRING`, or `BOOL`.

`TYPE` and `DOUBLE` values are not valid MATCH targets.

Each case shall contain exactly one function invocation.

Each case value shall have the same type as the target expression.

A case value shall be either a literal or a constant identifier whose value is known at compile time.

Duplicate case values are invalid. Duplicate values shall be detected by comparing their evaluated constant values.

Exactly one `DEFAULT` case is required. `DEFAULT` shall be the final case.

The target expression is evaluated exactly once.

Exactly one matching case is executed. If no other case matches, the `DEFAULT` case is executed. Cases do not fall through to subsequent cases.

Example:

```llmk
MATCH status
    0 User.Pending()
    1 User.Success()
    2 User.Failed()
    DEFAULT User.Unknown()
```

The following example is valid for a STRING target:

```llmk
MATCH command
    "start" Process.Start()
    "stop" Process.Stop()
    DEFAULT Process.Unknown()
```

The following are invalid:

- A MATCH target of type `TYPE` or `DOUBLE`.
- A MATCH statement without `DEFAULT`.
- A `DEFAULT` case that is not the final case.
- Duplicate case values.
- A case value whose type differs from the target type.

---

## 7.4 MATCH_RESULT

MATCH_RESULT handles a value of type `RESULT T`.

The target expression shall evaluate to a RESULT value.

MATCH_RESULT shall contain exactly two cases, in the following order:

- `SUCCESS(value)`
- `ERROR(error)`

Each case shall contain exactly one function invocation.

The target expression is evaluated exactly once.

Exactly one case is executed.

For a successful RESULT, the variable declared in `SUCCESS(value)` is bound to the successful value of type `T`.

For an error RESULT, the variable declared in `ERROR(error)` is bound to the error value of the standard library `Error` TYPE.

Each case variable is available only within its corresponding case and function invocation.

MATCH_RESULT does not support `DEFAULT`.

The case order shall not be changed, and neither case may be omitted.

Example:

```llmk
MATCH_RESULT result
    SUCCESS(value) User.HandleSuccess(value)
    ERROR(error) Logger.LogError(error)
```

The following are invalid:

- Using MATCH instead of MATCH_RESULT to handle a RESULT value.
- Omitting either case.
- Reversing the case order.
- Adding a DEFAULT case.
- Using a case variable outside its corresponding case.

---

## 7.5 FOR

FOR sequentially processes every element of an ARRAY.

Example:

```
FOR users User.Validate()
```

The current element is automatically passed as the first function parameter.

The current element shall not be specified explicitly in the FOR or PARFOR statement.

The invoked function may optionally accept one additional `REF TYPE` parameter.

Example:

```
VAR Statistics statistics = Statistics()

FOR users User.Validate(statistics)
```

Conceptually, each iteration performs:

```
User.Validate(user, statistics)
```

FOR processes elements in input order.

Every iteration shall execute.

---

## 7.6 PARFOR

PARFOR executes every element of an ARRAY independently.

Example:

```
LET ARRAY RESULT User results =
    PARFOR users User.Validate()
```

The current element is automatically passed as the first function parameter.

The current element shall not be specified explicitly in the FOR or PARFOR statement.

The invoked function shall accept exactly one parameter.

REF parameters are not permitted.

The execution order is implementation-defined.

PARFOR waits for all iterations to complete.

Returned values are collected into an ARRAY preserving the input order.

A failure in one iteration shall not prevent the execution of the remaining iterations.

---

## 7.7 Design Principles

The control flow system follows these principles.

- Function invocation is the fundamental execution model.
- Executable blocks are minimized.
- Nested control flow is avoided.
- Sequential and parallel execution are explicit.
- Shared mutable state is prohibited in PARFOR.
- Every control flow construct is deterministic.

Control flow is expressed by function invocation rather than executable blocks.
